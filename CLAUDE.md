# CLAUDE.md — Finance Tracker project context

Reference doc for working on this repo. Read this before making changes; update it when a documented decision changes.

## What this is

A local-first, open-source personal finance tracker (FastAPI + SQLite). Users track budget/spending/income across daily/weekly/monthly/quarterly/yearly views, with tiered bank connectivity: CSV/OFX import as the zero-config default, optional live sync via SimpleFin (user-supplied token, no bank credentials ever touch this app or a server we run). Goal is an open-source project anyone can one-click-run (Docker) and fork/extend, eventually packaged as a native desktop app via Tauri (`src-tauri/`, wraps the same FastAPI backend as a subprocess — no duplicated logic).

**Status:** all 5 planned phases are done — Dashboard, Accounts/Transactions, CSV/OFX import, and SimpleFin live sync are fully wired end-to-end, plus post-launch fixes from real usage: the dashboard shows one period at a time (not all-history), account balance is trustworthy (bank-reported when available, not just a raw transaction sum), two accounts can be merged into one, and SimpleFin no longer silently creates a duplicate account for something you've already CSV-imported. A first UI pass (from a Figma wireframe) reshaped the dashboard: renamed to "Overview," gained per-account filtering via a sidebar, and replaced the category-breakdown list with a donut chart. Remaining work is more UI polish (accounts-page issues flagged by real usage, not yet itemized) and whatever's next in `PLAN.md`'s "Later / unscheduled" section.

## Architecture

```
app/
  main.py          FastAPI entrypoint — includes all routers, runs migrations
                    (app.database.run_migrations()) at import time
  config.py        pydantic-settings Settings, reads .env
  database.py      SQLAlchemy engine/session, Base, get_db() dependency, run_migrations()
  models.py        Account, Category, Transaction, SimplefinConnection (SQLAlchemy 2.0 typed style)
  routers/         HTTP layer — one file per feature area
  services/        Business logic, called from routers
  templates/        Jinja2 — base.html (layout/nav) + page templates
  static/          css/style.css (design tokens + base styles), vendor/ (htmx, Chart.js)
migrations/        Alembic — env.py wired to app.database.Base/Settings, versions/ holds
                   real revision scripts (see the "Schema changes go through Alembic" note below)
```

**Router/service split — preserve this convention:**
- **Routers** are the "shape stub" layer: real `APIRouter`s with real prefixes/tags, `Depends(get_db)` injected even before it's used, module docstring explaining intent + `TODO:` notes. Until implemented, a router returns placeholder success data (`200` + `{"note": "stub — not yet implemented"}` or empty list/dict) — routers should not raise `NotImplementedError` themselves.
- **Services** are the "logic stub" layer: functions/classes with real signatures that `raise NotImplementedError("...")` until implemented. This is where actual business logic (aggregation math, CSV parsing, SimpleFin API calls) lives, kept out of route handlers.

When implementing a stub, replace both halves together: make the service function actually work, then have the router call it instead of returning the placeholder.

**HTML-rendering pattern (established in `routers/dashboard.py`, Phase 2):** a router that renders UI imports `templates` from `app.templating` (not from `app.main` — that would be a circular import, since `main.py` imports the routers). It checks `request.headers.get("hx-request") == "true"` to decide whether to return a full page (extends `base.html`) or just the inner fragment for an HTMX swap target. Keep `<script>` tags out of swapped fragments — HTMX doesn't execute scripts injected via a swap — so any JS that needs to react to new content (e.g. rebuilding a Chart.js chart) belongs in a page-level script listening for `htmx:afterSwap`, not inside the fragment template itself.

**When to use HTMX vs. a plain form (established in Phase 3):** not everything needs to be an HTMX partial. Infrequent, whole-record actions (create/edit an account) use a plain `<form method="post">` + a 303 redirect — works without JS, simplest code. Frequent, per-row actions (categorizing a transaction) use HTMX (`hx-post` + `hx-target="closest tr"` + `hx-swap="outerHTML"`) so there's no full-page reload. Pick based on frequency/graininess of the action, not by default.

**Select-then-act, for anything that isn't the page's single highest-frequency action (established in the Transactions page redesign, 2026-08-30):** once a page accumulates more than one or two occasional per-row actions (mark as transfer, tag reimbursable, resolve, delete), giving each its own permanent inline control clutters every row for the sake of things done rarely. Instead: a checkbox per row (`name="transaction_id"`), a fixed action bar (hidden until something's checked, `.bulk-action-bar`/`.bulk-action-bar--visible` in `style.css`) whose buttons `hx-post` to `/transactions/bulk/{action}` with `hx-include="[name='transaction_id']:checked, ..."` to gather whatever's checked. The one exception is whatever *is* the page's highest-frequency action (category assignment, here) — that stays its own always-visible per-row control; routing the most common thing into select-then-act would add friction to it. A small vanilla-JS file (`static/js/transactions.js`) tracks the "N selected" state via event delegation on `document` rather than per-checkbox listeners, so it survives an HTMX swap replacing the whole table without needing to re-bind anything — the same reason `dashboard.js` listens for `htmx:afterSwap` instead of running once at load.

**Bulk actions need the current filter/page carried back through the request, or the response resets the view (established alongside select-then-act):** the action bar's buttons live *outside* the HTMX swap target (so the bar itself doesn't flicker on every action), but the current `view`/`page` live *inside* it as hidden inputs, freshly rendered on every fragment render — the bar's `hx-include` reaches in and grabs them. Same "state that must stay in sync belongs inside the swap target" principle as the dashboard's account sidebar (see below), just applied to two hidden form fields instead of nav state. Every bulk route re-renders at the *same* filter/page the action was taken from, never resetting to page 1.

**List views need eager loading, not just pagination, once there's real data (established in the Transactions page redesign):** `transactions/_row.html` reads `transaction.account`, `.category`, `.tags`, `.transfer_pair` — each an unguarded lazy load. At 1,000+ rows with no eager loading, that's thousands of extra queries for one page render; this was the actual cause of a reported "switching views feels slow" complaint, not just a missing LIMIT. `routers/transactions.py::_base_query()` is the pattern: `joinedload()` for many-to-one relationships (one extra JOIN, no row multiplication), `selectinload()` for many-to-many (`tags`) — a JOIN there would multiply rows per tag. Reach for this on any new list view that renders more than a handful of relationship-heavy rows, before assuming pagination alone will fix perceived slowness.

**httpx's `TestClient` needs a dict-with-list-value for a repeated form key, not a list of tuples (established while testing bulk actions):** `data=[("transaction_id", "1"), ("transaction_id", "2")]` (the `requests`-style way) silently produces an *empty* request body with httpx — use `data={"transaction_id": ["1", "2"]}` instead. Real browser/HTMX-submitted forms were never affected (they already produce a normal repeated-key body); this only bit test code POSTing a list to an endpoint.

**Everything that must stay in sync belongs inside the HTMX swap target (established in `dashboard/_content.html`, UI pass 1):** HTMX only updates the element named by `hx-target` — anything outside it (a page heading, a sidebar's "active" state) goes stale on a swap unless it's also inside that element. The dashboard's account sidebar lives inside `#dashboard-content`, not next to it, specifically so its "active" highlight and the page's `<h1>` (which shows the selected account's name) update correctly when an account/range/period switch swaps that region. If a new element needs to reflect state that a swap can change, put it inside the swapped fragment.

**Rendering money in a template:** always use the `money` filter (`{{ amount | money }}`, registered in `app.templating`), never hand-rolled `"%.2f"|format(...)` with a literal `$` — that produces `$-19.99` instead of `-$19.99` for negative values. Exception: values that are already-unsigned magnitudes (e.g. `aggregation.py`'s `totals.income`/`totals.spending`/`by_category[].total`, which are deliberately abs()'d) don't need it, though using it anyway is harmless.

**Dashboard = one period at a time, not all-history (redesigned post-Phase-4, per real usage feedback):** `GET /dashboard/{range_type}?offset=N` shows the *current* period at `offset=0` (today / this week / this month / this quarter / this year), stepping back one period per `offset` increment — never a chart spanning an account's entire history. `aggregation.get_period_dashboard()` is the one function that computes this; don't reintroduce an "all transactions bucketed by granularity" path. If you add a new range-shaped feature, it should default to the current period too, not "everything."

**Multi-step flows without server-side session state (established in `routers/import_csv.py`, Phase 4):** the CSV import flow (upload → adjust mapping → confirm) needs state to survive multiple requests, but there's no session/pending-import table. Instead: the uploaded file is staged to a token-named temp file (OS temp dir — see `IMPORT_TMP_DIR`, deliberately outside `data/`, which is for real app data, not transient staging), and every other piece of state (account_id, file_kind, the column mapping) round-trips through hidden form fields on each step's response. Reach for this pattern before adding a new DB table just to hold "in-progress" state.

**External API integrations get verified against the real thing, not memory (established in `services/simplefin_client.py`, Phase 5):** before writing the SimpleFin client, its protocol assumptions (plain-text claim response, embedded Basic Auth that httpx resolves automatically, the 90-day hard cap / 45-day recommended window on `start-date`) were confirmed live against SimpleFin's own demo bridge with `curl`/a throwaway script — not just read from docs or recalled. The automated test suite still mocks `httpx` (no network dependency in CI), but that manual verification pass is what the tests are asserting against. Do this for any new external API, not just SimpleFin.

**Never silently auto-create an Account for data from an external source (established post-Phase-5, real usage feedback):** `simplefin_sync.py` used to auto-create a local `Account` for every remote SimpleFin account with no local match — this caused a real duplicate (a CSV-imported credit card and its later SimpleFin connection ending up as two separate, un-linked accounts with different partial balances). Now every not-yet-linked account stops at a one-time review step (`simplefin/new_accounts.html`) offering "create new" or "link to an existing account" before anything is created — see `simplefin_sync.partition_response()`/`create_new_account()`/`link_to_existing_account()`. If a future import/sync source is added, give it the same gate rather than reintroducing silent auto-creation. `app/services/account_merge.py` exists to clean up accounts that already got split this way before the gate existed — it's a cleanup tool, not a substitute for the gate.

## Data model (`app/models.py`)

- **Account** — `id`, `name`, `institution` (nullable), `account_type` (free string: "checking"/"savings"/"credit"/etc, no enum), `source` (default `"manual"`; `"manual"` or `"simplefin"`), `created_at`, `starting_balance` (nullable — optional user-entered baseline, see `services/balances.py`), `simplefin_account_id`/`simplefin_connection_id` (nullable — set only for `source == "simplefin"`, used to match this account across resyncs instead of recreating it), `reported_balance`/`reported_balance_as_of` (nullable — SimpleFin's own current balance for this account, refreshed every sync). Has many `transactions`.
- **Category** — `id`, `name` (unique), `kind` (default `"expense"`; `"income"` or `"expense"`). Has many `transactions`. No category-management UI exists yet — `app/services/categories.py::ensure_default_categories()` seeds a fixed starter set on first startup (idempotent, only fires on an empty table) so the categorization UI has something to offer.
- **Transaction** — `id`, `account_id` (FK), `category_id` (nullable FK), `date`, `amount` (`Numeric(12,2)`, **signed**: positive = income, negative = spending — deliberate, simplifies aggregation math, keep this convention), `description`, `external_id` (nullable — dedup key for re-imports/syncs), `balance` (nullable — the account's running balance as of this transaction, when the import source reports one; see `services/balances.py`), `is_transfer` (default `False`) / `transfer_pair_id` (nullable, self-FK — see `services/transfers.py` and the transfer convention below; pairing is optional, marking one side alone is a valid end state), `reimbursed` (default `False` — the manual "paid me back" checkbox, only meaningful alongside the `reimbursable` tag), `tags` (many-to-many via `TransactionTag`, see below).
- **Tag** — `id`, `slug` (unique), `name`. A small, fixed, **code-owned** set (`app/services/tags.py::SYSTEM_TAGS`) — unlike `Category`, there's no way for a user to create one. Currently `reimbursable` (backs the "owed to me" tracking flow, paired with `Transaction.reimbursed`) and `subscription` (reserved for recurring-payment detection, a later phase — usable for manual tagging today, nothing auto-applies it yet). `app/services/tags.py::ensure_system_tags()` seeds/repairs these on every startup (idempotent per-slug, not empty-table-only — see the seeding convention below).
- **TransactionTag** — pure join table (`transaction_id`, `tag_id`), no extra columns; per-tag state that only makes sense for one specific tag (like `reimbursed`) lives on `Transaction` directly rather than here.
- **SimplefinConnection** — `id`, `access_url` (embeds HTTP Basic Auth credentials — treat as a secret, never render it into a template), `created_at`, `last_synced_at`. In practice there's ever only one row; it's still a table (not a `Settings` value) because one access URL can cover multiple bank accounts, and a single global setting doesn't fit that. This resolved the token-storage question that used to be an open decision here.

`external_id` in practice: OFX and SimpleFin imports use the source's own stable id (`FITID` for OFX, `id` for SimpleFin transactions). CSV imports don't have one, so `csv_importer.py` derives a hash of (date, amount, description) — meaning two genuinely different transactions that happen to share the exact same date/amount/description would collide; within a single file this is disambiguated with a counter suffix, but a stray same-day/same-amount/same-description transaction reappearing across two *separate* CSV exports could still be mistaken for a duplicate and skipped on reimport. A real limitation of CSV lacking stable ids, not a bug to "fix" without a better signal to key off.

**"What's my balance" is never a raw sum (established post-Phase-4, real usage feedback):** never compute an account's displayed balance as just `sum(transaction.amount)` — that will not match a real bank balance unless every transaction the account has ever had was imported, which is the unusual case, not the default. Always go through `app.services.balances.resolve_balance()`, which does the four-tier fallback (`Account.reported_balance` from a SimpleFin sync → transaction-level reported `balance` from CSV/OFX → `Account.starting_balance` + net → honestly-labeled net-only) and returns an `AccountBalance` with a `source` your template must surface (see `templates/macros.html`'s `balance_caption`), not just the number alone.

**Transfers between the user's own accounts are excluded from income/spending, but still count toward balance (established in `app/services/transfers.py`, six-feature batch Phase A):** a transaction the user marks `is_transfer` (e.g. a credit-card payment from checking) is real money moving between their own accounts, never real income or spending — `aggregation.get_period_dashboard()`'s base query filters `Transaction.is_transfer.is_(False)` before computing totals/buckets/by_category, for both a single-account view and "all accounts." `balances.py` is deliberately untouched: a transfer genuinely changed that account's balance, so it must still count in the `starting_balance + net` tier. When a UI surfaces a number that's had transfers filtered out of it, say so (`aggregation.py`'s `transfer_count`, surfaced as "excludes N transfers this period" on the Overview dashboard) — same transparency principle as `balance_caption`, applied to a different kind of "the number isn't the naive sum" situation. Pairing the two sides of a transfer (`transfer_pair_id`) is optional, never required — marking one side alone (e.g. the other account isn't tracked in this app) is a fully valid, permanent end state. `link_transfer_pair()` confirms a specific pair; the Transactions page gets there by having the user select both sides themselves and mark them together (see the select-then-act convention below), not through a suggested-candidate heuristic — an earlier `find_transfer_candidates()` was retired once nothing called it anymore. Any code that deletes a transaction or moves it to a different account (see `account_merge.execute_merge()`) must stay transfer-aware — clear a deleted transaction's partner (`transfers.clear_pair_on_delete()`) and collapse a pair that a merge left on the same account, or `transfer_pair_id` can end up pointing at a row that no longer represents a real transfer.

**Tags are a small, fixed, code-owned vocabulary — never a place to let the user free-form label things (established in `app/services/tags.py`, six-feature batch Phase B):** `Tag`/`TransactionTag` is a real many-to-many table, not two booleans on `Transaction`, but that's for mechanism reuse (see the model doc above), not extensibility — there's still no UI to create a new tag, and `SYSTEM_TAGS` in `tags.py` is the single source of truth for which ones exist. A new system tag is a code change (add to `SYSTEM_TAGS`), not a feature. `ensure_system_tags()` seeds/repairs per-slug on every startup, unlike `ensure_default_categories()`'s empty-table-only check — the difference exists because tags are never user-renamed or deleted, so there's nothing user-set to clobber by re-checking every time. Tag toggling was originally a per-row HTMX control (matching categorization); the Transactions page redesign (2026-08-30) moved it into the page's select-then-act bulk action bar instead — see the select-then-act convention below for why, and `docs/2026-08-30-transactions-page-redesign.md` for the full reasoning. `POST /transactions/{id}/tags/{slug}/toggle` no longer exists; tag mutation goes through `POST /transactions/bulk/reimbursable` now.

**Flagging a transaction never retroactively changes past totals (established alongside `reimbursed`, six-feature batch Phase B):** tagging a transaction `reimbursable`, or later checking it off as `reimbursed`, doesn't touch `aggregation.py` at all — it was real spending when it happened and stays real spending in every period it already appeared in; these are purely status fields for the reimbursement list/tab, not aggregation inputs. If a future feature wants a transaction to stop counting toward normal totals (the way `is_transfer` does), that has to be an explicit, deliberate exclusion added to `aggregation.py`, not an incidental side effect of tagging something.

**Schema changes go through Alembic (established Phase 0 of the six-feature batch, 2026-08-29):** `migrations/` at the repo root, wired to the app's own `Base.metadata` and `Settings.database_url` (see `migrations/env.py`'s docstring) — not a separate, hardcoded connection. `app.database.run_migrations()` (called at startup from `main.py`, replacing the old `Base.metadata.create_all()` + `ensure_schema_migrations()` pair) handles two cases: a genuinely empty database runs every migration from scratch (`alembic upgrade head`); an existing pre-Alembic database (the app's tables already exist, but there's no `alembic_version` table yet) gets stamped at `migrations/versions/0001_baseline_schema.py`'s fixed revision id (`"0001"`, not the string `"head"` — see `run_migrations()`'s docstring for why that distinction matters once a second migration exists) before running `upgrade head` normally. Any new column or table goes into a real Alembic revision (`alembic revision --autogenerate -m "..."`, hand-reviewed before committing, from repo root — `env.py` falls back to the app's real configured database only when nothing else has set a URL, so a plain CLI invocation naturally targets `data/finance.db`) instead of a hand-maintained list of raw `ALTER TABLE` strings. The old `_ADDED_COLUMNS` stopgap and `ensure_schema_migrations()` are gone, not kept alongside the new system. `env.py` runs with `render_as_batch=True` unconditionally — SQLite's `ALTER TABLE` can't add a constraint or drop a column at all, so every migration that does either needs Alembic's batch mode (table-recreate-under-the-hood), and a column-only add works fine in batch mode too, so there's no reason to toggle it per-migration. A `NOT NULL` column added to a table that already has real rows (the normal case for every migration after the baseline) needs a `server_default` for the `ALTER`/recreate to succeed, typically dropped in a second step right after so the column's *ongoing* default lives only at the Python/ORM level (`mapped_column(default=...)`), matching every other column — see `migrations/versions/1abc77cdafa9_add_transfer_columns_to_transactions.py` for the pattern.

**Simulating "a pre-Alembic database" in a migration test means hand-written DDL, not `Base.metadata.create_all()` (established during Phase A, six-feature batch):** `Base.metadata` reflects *today's* full set of models — it only matched "the legacy schema from before Alembic existed" at the exact moment Phase 0 shipped, and silently drifts out of sync the moment any later phase adds a column, since a real legacy database (by definition never touched by Alembic) can never have picked up anything a later Alembic migration introduced. `tests/test_migrations.py`'s `_build_legacy_pre_alembic_database()` hand-writes the frozen legacy DDL instead (same spirit as the old `tests/test_database.py`'s `_pre_migration_engine()`, which did the same for the `_ADDED_COLUMNS` stopgap) — keep doing this rather than reaching for `create_all()` when a future phase needs to test the stamp path again.

## Conventions

- SQLAlchemy 2.0 typed style throughout: `Mapped[...]` / `mapped_column(...)`, not the legacy `Column(...)` style.
- Full type hints everywhere, including `str | None` union syntax (Python 3.10+; base image is `python:3.12-slim`).
- Every module opens with a docstring stating purpose, and explicit `TODO:` comments for known-deferred work — keep adding these as you go, don't silently defer things.
- `requirements.txt` pins exact versions (`==`), no ranges.
- No linter/formatter configured yet (no ruff/black/mypy) — match existing style by hand until one is added.

## Frontend direction (Phase 1+)

**Stack: server-rendered Jinja2 + HTMX + Chart.js, vanilla CSS. No JS framework, no npm/build step.**

Rationale: keeps "clone and run" trivial for forkers (no `npm install`/build pipeline), and means the eventual Tauri desktop shell has nothing extra to package — it just points a webview at the same FastAPI server. `jinja2` and `python-multipart` are already in `requirements.txt` for this. Vendor HTMX and Chart.js as local static files rather than loading from a CDN — this app is meant to work fully offline/local-first.

**Visual style guideline (starting point, revise as pages get built):**
- Clean, minimal budgeting-app aesthetic — think restrained dashboard, not marketing-site flashy. Card-based layout for account summaries, category breakdowns, and totals.
- Chart.js for spend/income within the selected period — see the dashboard convention below for what "period" means.
- Light + dark mode via CSS custom properties (`:root` variables, no separate stylesheets), respecting `prefers-color-scheme` by default.
- Color used sparingly and meaningfully: green/red reserved for income/expense signal (matching the model's signed-amount convention), not used decoratively elsewhere. Distinguishing many small categories (the category-breakdown donut) uses a separate categorical palette (`--cat-0`..`--cat-7` in `style.css`, light + dark variants) — deliberately different hues from income/expense/accent, cycled by index, not tied to any specific category.
- HTMX handles the interactive bits (range switching, live-updating fragments) — server returns rendered HTML fragments, not JSON, to HTMX-triggered requests. (`dashboard.py`'s own TODO already anticipates this: "return an HTMX-rendered template fragment instead of raw JSON.")

**When writing CSS careful of selector specificities. It's easy to generate CSS classes that cancel each other out (established from a real bug, UI pass 1 round 2):** `.card + .card { margin-top: 1rem }` was written assuming cards always stack vertically in plain block flow (true when it was added) — but `.card-grid`'s children are laid out side-by-side, and the sibling-combinator selector fires there too, since it only checks DOM order, not visual layout. Combined with grid's default `align-items: stretch`, this made the first card in every `.card-grid` render visibly taller than its siblings. Any new `.card`-based layout should assume this rule applies unless explicitly canceled (`.card-grid > .card + .card { margin-top: 0; }` already does this for grids) — check for stacking-context-specific rules like this one before reusing a class in a new layout context.

**A second flavor of the same lesson, from the Transactions page redesign round 2 (2026-08-30): a bare single-class selector can silently lose to an existing compound selector.** `.description-cell { white-space: normal }` (specificity 0-0-1-0) lost the cascade to the already-existing `.txn-table td { white-space: nowrap }` (0-0-1-1) regardless of which was declared later in the file — the more specific rule always wins on a tie in matched elements, full stop. The bug was invisible in the rendered HTML (both rules "applied," one just never took effect) and only showed up as a status pill visually overlapping the next table column in an actual screenshot — grep-checking the markup wouldn't have caught it. When adding a rule meant to override behavior from a `<parent-selector> <child-tag>`-shaped rule already in the file (`.txn-table td`, `.nav a`, etc.), match that same prefix (`.txn-table td.description-cell`) rather than assuming a later, simpler selector will win — check the losing rule's specificity against what it's supposed to override, not just whether the new rule looks correct in isolation. Also worth remembering: `table-layout: auto` (the default) lets a `max-width` on a `<td>` be overridden by content that "doesn't need" to wrap — a fixed-width `<colgroup>` plus `table-layout: fixed` is what actually makes per-column width constraints reliable in a table.

- No category-management UI — categories come from a fixed default set (`app/services/categories.py`).
- No budget-planning logic behind the `/plan/` page yet — it's a nav stub, not a feature; what it should actually do (per-category targets? monthly budget vs. actual?) hasn't been scoped.
- `/settings/` is a nav stub too — nothing to configure yet, and what it should hold (theme override? default dashboard range? SimpleFin connection management?) hasn't been scoped either.
- Accounts-page UI issues flagged by real usage, not yet itemized — waiting on specifics before the next UI-polish pass.
- OFX parsing is a pragmatic regex extractor for the standard single-account `<STMTTRN>` structure, not a full SGML/XML parser — see `csv_importer.py`'s `parse_ofx` docstring for what it doesn't handle.
- No background/scheduled SimpleFin sync (manual "Sync now" only) and no multi-bridge "Connect another bank" UI (the data model supports it, the UI doesn't yet).
- No pending-transaction reconciliation for SimpleFin — a transaction that transitions from pending to posted could in theory get a new id and show up as an extra row.
