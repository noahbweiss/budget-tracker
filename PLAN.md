Also found: SQLite `:memory:` test databases are connection-scoped — `TestClient` runs sync route handlers in a worker thread, which can grab a different pooled connection than the one `Base.metadata.create_all()` ran DDL on, producing "no such table" errors. Fixed with `poolclass=StaticPool` in `tests/conftest.py`'s `db_session` fixture.

## Phase 4 — CSV/OFX import ✅ (2026-08-28)

- [x] `app/services/csv_importer.py`: `parse_csv()` and `parse_ofx()`. CSV mapping is a flexible auto-detector (`detect_mapping()` matches common header-name variants — "Date"/"Transaction Date"/"Posted Date", "Description"/"Memo"/"Payee"/"Name", single "Amount" or split "Debit"/"Credit") rather than a hardcoded per-bank preset list — there's no real bank sample data in this repo to build or verify named presets against, so an honest general detector plus manual override beats fabricated "Chase preset"/"Amex preset" support. Handles `$`/comma-formatted amounts, parenthesized negatives, and several date formats. `parse_ofx()` is a deliberately hand-rolled regex extractor (not a real SGML/XML parser — OFX 1.x tags often aren't closed) covering the common `<STMTTRN>` case; uses OFX's own `FITID` as the dedup id instead of a synthetic hash, since it's a real stable id CSV doesn't have. 26 tests (`tests/test_csv_importer.py`).
- [x] `app/routers/import_csv.py`: full upload → preview/mapping → confirm flow. The uploaded file is staged to a temp path (OS temp dir, not `data/`) keyed by a token; account_id, file_kind, and the confirmed column mapping round-trip through hidden form fields between steps — no new DB table or server-side session needed. Column-mapping adjustment is HTMX (live-updates the preview table on change, matching the "frequent small interaction → HTMX" convention); "Confirm import" and "Cancel" are plain form posts (matching the "whole-record action → plain form" convention). Duplicate rows (by `external_id`, scoped to the account) are skipped and reported, not silently dropped or double-inserted — verified live by uploading and confirming the same file twice. 12 tests (`tests/test_import_router.py`).
- [x] Upload + column-mapping + preview UI: `import/{index,preview,_preview_body,result}.html`. Preview is capped at 50 displayed rows (with a "…and N more" note) but still imports every row on confirm.

**Deliberately not done:** OFX edge cases beyond the standard single-account `<STMTTRN>` structure (multi-account files, unusual field ordering) — would need a real parser library (e.g. `ofxparse`), a new dependency not taken on for a format most banks only offer as a secondary export option to CSV. Per-row partial-failure handling — a single unparseable row fails the whole parse with one error message, rather than importing the good rows and flagging the bad ones individually.

Caught during end-to-end verification against a real uploaded file (same lesson every phase so far — router/unit tests didn't catch this since neither exercises the actual multipart upload path): none this time, actually — first phase where the live walkthrough (debit/credit auto-detection, `$`-prefixed amount, an intentional exact-duplicate row, full confirm → re-upload → dedup round trip) matched the tests exactly. Recorded here anyway, since the pattern of "verify against real data before calling it done" is what caught the Phase 2 and Phase 3 bugs and is worth keeping regardless of whether it finds something every time.

## Post-Phase-4 fixes — real-usage feedback (2026-08-28)

Once real data was actually imported and used, two things turned out to be wrong in ways the phase-by-phase build-out hadn't surfaced:

- [x] **Dashboard redesigned from "all-history chart" to "one period at a time."** The original Phase 2 design bucketed *every* transaction ever, by range_type granularity, into one long chart — so "daily" showed a bar for every single day the account had ever existed, not what a budgeting dashboard should default to. Replaced with `aggregation.get_period_dashboard(db, range_type, offset)`: each range shows the *current* period (today / this week / this month / this quarter / this year) by default, navigable via `offset` (prev/next buttons, 0 = current). Within a period, the chart breaks it into a finer sub-bucket — a month into its days, a quarter into its months, a week into its days — zero-filled for every sub-period, not just ones with transactions, so a sparse month doesn't look like it only has 3 days. "Daily" has no chart (nothing to sub-divide a single day into without time-of-day data) — just totals and category breakdown. The current period also shows a "Day X of Y" progress note (e.g. "Day 59 of 92" for a quarter). This is a full replacement of `bucket_transactions()`, not an addition alongside it — the old all-history behavior is exactly what was wrong. 26 tests (`tests/test_aggregation.py`, rewritten), heavy on date-math edge cases (quarter/year boundaries, leap years) since that's where the real risk was.
- [x] Nav/route-level tests updated (`tests/test_health.py`) for offset navigation and the daily-has-no-chart case.
- [x] **Account balance made trustworthy.** The account "Net" figure was a pure sum of tracked transactions — which never matches a real bank balance if any account activity happened before the first imported transaction (the normal case). Three-tier fix, most trustworthy first: (1) if any imported transaction carries the bank's own reported balance (a new optional `Balance` column in the CSV mapping — `Transaction.balance`, nullable), the *latest* one is shown, exact, no computation involved; (2) else `Account.starting_balance` (new, optional, user-entered on the account edit form) plus the sum of tracked transactions; (3) else the raw net, now honestly labeled "Net of tracked transactions only" instead of implying it's a real balance. Re-uploading a CSV with `Balance` now mapped **backfills** the balance on already-imported transactions that were missing it (matched by `external_id`), rather than needing a from-scratch reimport — reported separately in the import result ("filled in the balance on N existing transactions"). Both new columns needed a real migration path since this shipped after real user data already existed: `Base.metadata.create_all()` only creates missing tables, never alters existing ones, so `app.database.ensure_schema_migrations()` (new, tiny stopgap until Alembic) does the `ALTER TABLE` — verified live against an actual pre-migration SQLite file (hand-built with the old schema), not just the in-memory test. `app/services/balances.py` (6 tests), CSV importer balance detection/parsing (7 tests), import-router capture/backfill (2 tests), account router/template (4 tests) — 19 new tests total plus the 3 migration tests in `tests/test_database.py`.

## Phase 5 — SimpleFin sync ✅ (2026-08-28)

- [x] Resolved the token-storage decision: a dedicated `SimplefinConnection` table (`app/models.py`), not `config.py`'s old `simplefin_access_url` setting (removed, along with the `.env`/`.env.example` entry for it) — one access URL can cover multiple bank accounts, which a single global setting never fit.
- [x] `app/services/simplefin_client.py`: `exchange_setup_token()` and `get_accounts_and_transactions()`, implemented against the real protocol — verified live against SimpleFin's own demo bridge (beta-bridge.simplefin.org) during development, not from memory: confirmed the claim response is plain text (not JSON), that httpx resolves the access URL's embedded Basic Auth automatically, that re-claiming an already-used setup token 403s, and that `start-date` has a hard 90-day cap and a 45-day "recommended" ceiling (informational, in the response's `errors` array, not a failure) — hence `DEFAULT_SYNC_LOOKBACK_DAYS = 30`. 6 tests (mocked httpx — the live-network verification was manual, not baked into the suite).
- [x] `app/services/simplefin_sync.py` (new): turns a raw `/accounts` response into local `Account`/`Transaction` rows — pure logic, no network, tested with a fixture modeled on the real captured demo response. Accounts matched across syncs by `(simplefin_connection_id, simplefin_account_id)` so a resync updates rather than duplicates; name/institution/account_type are only set on first creation (never clobber a user's local edits on resync); balance is always refreshed (SimpleFin's own current balance, not computed — flows into `resolve_balance()`'s balance fallback as a new highest-priority tier, ahead of CSV/OFX's transaction-level reported balance). Transaction description prefers `payee` (merchant name) over the more generic `description` field when both are present. Holdings (investment positions) are present in the API but deliberately not imported — this app tracks cash-flow transactions, not a brokerage portfolio. 9 tests.
- [x] `app/routers/simplefin.py` + `simplefin/index.html`: connect form (paste setup token) when no connection exists, else a connected-status view (connected/last-synced dates, linked accounts, "Sync now"). Connecting triggers an immediate first sync; if that sync fails, the connection is still saved (not rolled back) so "Sync now" can retry rather than losing the whole connection over a transient error. The access URL — a real bearer credential — is never rendered into any template; a dedicated test asserts this. 8 tests.

**Verified live end-to-end against the real SimpleFin demo API** (not just mocks): connected, synced 3 real accounts (Savings/Checking/Empty) with correct guessed account types, correct institution, correct reported balances; synced a second time and got "0 accounts added, 3 updated · 0 transactions imported, 116 already up to date" — confirmed no duplicates, matching the exact dedup behavior CSV/OFX import already established.

**Deliberately not done:** no background/scheduled sync — this is a "click Sync now to check for updates" app, not an always-on service (matches the local-first, no-server-we-run design). No multi-bridge UI — the router supports it structurally (one `SimplefinConnection` row could become several), but there's only ever one "Connect" screen for now. No pending-transaction handling — a transaction transitioning from pending to posted could in theory get a different id and appear as a new row; not building reconciliation for this until it's an observed real problem, not a hypothetical one.

## Post-Phase-5 fix — account merging + discovery gate (2026-08-29)

Confirmed by real usage: connecting SimpleFin to an account already CSV-imported created a second, separate local `Account` for the same real-world credit card — SimpleFin only pulls the last ~90 days, so the two accounts showed different partial histories and different balances, with no link between them. Two-part fix:

- [x] **`app/services/account_merge.py` (new):** combine two `Account`s that turned out to be the same real-world account. `find_duplicate_candidates()` matches transactions across the two by (date, amount) — CSV's external_id (a hash of date+amount+description) and SimpleFin's own transaction id never coincide even for the identical real transaction, so ordinary external_id dedup can't catch this overlap; matching by (date, amount) alone casts a wide net on purpose, since the actual duplicate judgment is left to a human review step (`accounts/merge_preview.html`) rather than silently auto-discarding anything. `execute_merge()` acts on whatever was confirmed: unmatched transactions and rejected pairs move to the surviving account, confirmed-duplicate pairs are discarded (source's copy only — target's survives), SimpleFin linkage/reported balance transfers to the target only if it doesn't already have its own, and the source account is deleted. Caught a real SQLAlchemy ordering bug during TDD: reassigning a transaction's FK and deleting its old parent account in the same flush let the ORM's cascade-cleanup null out the FK before the reassignment was recognized, violating the NOT NULL constraint — fixed with an explicit `db.flush()` between the two steps. 10 service tests + 7 router tests (`app/routers/accounts.py`'s new `/accounts/merge*` routes).
- [x] **Discovery gate, so it doesn't happen again:** `app/services/simplefin_sync.py` no longer auto-creates an `Account` for every remote SimpleFin account with no local match. `partition_response()` splits a sync into accounts already linked locally (synced immediately via `sync_matched_accounts()`, no interruption — this is the common case on every regular "Sync now") and accounts with no match yet, which stop at a review step (`simplefin/new_accounts.html`) offering, per account, "create new" or "link to an existing account" — reusing the account-picker pattern already established elsewhere in the app. Only on confirm does `create_new_account()` or `link_to_existing_account()` actually touch the database. This applies on every connect/sync, not just the first — a later-added bank account gets the same one-time check the moment it's first seen. 10 service tests + 9 router tests (rewritten; `apply_sync_response()`, the old do-everything-silently function, is gone — replaced, not kept alongside the new gated path).

**Verified live end-to-end against the real SimpleFin demo API** for both pieces — not just mocks: (1) seeded a scenario mirroring the real one (a CSV-style account with older history, a second account with an overlapping recent window and different description formatting for the same charges), ran a merge, confirmed the preview correctly caught the real overlapping charges as candidate duplicates despite differently-formatted descriptions, and confirmed the final state was exactly right after confirming; (2) seeded a pre-existing manual account, connected to the real demo bridge, confirmed the review step appeared for all 3 real accounts with zero auto-created, linked one to the pre-existing account and created the other two as new, confirmed the linked account kept its own name but gained SimpleFin's real balance and transactions, and confirmed a follow-up sync went straight through with no review step re-appearing.

### Round 2 — itemized fixes from real usage (2026-08-29)

## Six-feature batch, Phase 0 — Alembic migrations ✅ (2026-08-29)

First phase of the six-feature batch (`docs/2026-08-29-feature-plan.md`) — adopted Alembic ahead of that batch's schema work, replacing the `_ADDED_COLUMNS`/`ensure_schema_migrations()` stopgap this project had been carrying since Phase 4 (the existing TODO in `database.py`/`main.py` this closes out).

- [x] `migrations/` at the repo root (`alembic init`), `migrations/env.py` wired to `app.database.Base.metadata` for autogenerate and to `app.config.settings.database_url` for the connection — with a load-bearing detail: the URL fallback only fires when nothing's already set one on the `Config` object, so `app.database.run_migrations()` can point Alembic at a throwaway database for tests without touching the real one, while a bare CLI `alembic ...` invocation still falls back to the app's real configured database.
- [x] `migrations/versions/0001_baseline_schema.py` — one revision capturing the exact schema this app already had (autogenerated against an empty database, verified with `alembic check` to produce zero further diff against `app/models.py`, then hand-edited only to give it a stable id, `"0001"`, instead of a random hash).
- [x] `app.database.run_migrations()` (replacing `Base.metadata.create_all()` + `ensure_schema_migrations()`, called from `main.py` at startup): a genuinely empty database runs every migration from scratch; an existing pre-Alembic database (real app tables present, no `alembic_version` table yet) gets stamped at `"0001"` specifically — not the string `"head"`, since that would silently skip any migration added after the baseline the next time a *different* still-unmigrated pre-Alembic database is seen — before running `upgrade head` normally.
- [x] The old `_ADDED_COLUMNS` list and `ensure_schema_migrations()` are gone, not kept alongside the new system. `tests/test_database.py` (which tested the old function) replaced by `tests/test_migrations.py` (3 tests: upgrade-from-empty, stamp-and-preserve-data-on-a-pre-alembic-database, idempotency) — using real on-disk SQLite files via `tmp_path`, not `:memory:`, since Alembic opens its own connection to the given URL and an in-memory database is scoped to a single connection.

**Caught during end-to-end verification against the real `data/finance.db`** (same discipline as every phase before this one — and this time it actually caught something): the first draft of `migrations/env.py` set the database URL from `settings.database_url` *unconditionally*, clobbering the URL `run_migrations()` had already set for its test-database override. Running the new test suite against that draft caused it to silently operate on the real `data/finance.db` instead of the tests' throwaway files — one test's stamp call landed for real, which (by good fortune, not by design) was actually the same correct outcome `run_migrations()` was always going to produce for that database on its next real startup anyway. Verified no harm done: row counts (3 accounts, 1283 transactions, 11 categories) and the transaction-amount sum matched a pre-incident backup exactly, and the resulting schema was byte-for-byte what `app/models.py` describes. Fixed by making the fallback conditional (only set the URL if nothing already has). Worth remembering alongside this project's other "verify against real data, not just mocks" lessons: that discipline also needs to extend to *migration tooling itself* — a test suite that touches a database is not automatically isolated just because it uses a temp path, if the code under test has its own opinion about which database to use.
- [x] Backed up `data/finance.db` before the final verification pass, out of caution, even after confirming no damage — a habit worth keeping for any future migration work, not just this one.

**Deliberately not done:** no data migration logic beyond the schema itself (this phase only had to describe tables/columns that already existed); no automatic `alembic upgrade head` documented as a manual step in the README, since it runs automatically at startup exactly like `create_all()` used to.

## Six-feature batch, Phase A — Transfers ✅ (2026-08-29)

First user-facing feature of the batch (`docs/2026-08-29-feature-plan.md`) — the credit-card-payment-counted-as-income problem the user opened the whole batch with. Sequenced first per the plan: `aggregation.py`'s "what counts as spending" logic only needed touching once, before Budgets (Phase D) has to reuse the same exclusion.

- [x] `Transaction.is_transfer` (default `False`) / `transfer_pair_id` (nullable, self-FK) — new Alembic revision `1abc77cdafa9_add_transfer_columns_to_transactions.py`, chained after a second new migration (below). Pairing is optional by design (confirmed decision, not an oversight): marking one side alone is a fully valid, permanent end state.
- [x] `app/services/transfers.py`: `mark_as_transfer`/`unmark_transfer` (unmark clears *both* sides of a pair, not just the one called on), `find_transfer_candidates` (opposite sign, same magnitude, different account, ±3 days, not already paired — same wide-net-then-human-confirms spirit as `account_merge.find_duplicate_candidates()`), `link_transfer_pair` (sets both sides symmetrically), `clear_pair_on_delete` (for callers that delete a transaction that might be paired).
- [x] `aggregation.get_period_dashboard()` excludes `is_transfer` transactions from `totals`/`buckets`/`by_category` (one filter on the shared base query, so single-account and all-accounts views both get it for free) and reports `transfer_count` for the period, surfaced on the Overview dashboard as "Excludes N transfers this period" — `balances.py` is untouched on purpose, since a transfer genuinely still changed the account's balance.
- [x] `POST /transactions/{id}/transfer` (toggle, HTMX row swap, inline candidate suggestions when newly marked and unpaired) and `POST /transactions/{id}/transfer/link` (confirm a specific candidate) in `routers/transactions.py`; `transactions/_row.html` gained a Transfer column (badge + pair note when linked, a candidate `<select>` + "Link" when marked-but-unpaired, "Mark transfer" otherwise) — per-row HTMX action, matching the existing category-`<select>` convention rather than a whole-page review gate, since a user marks transfers one at a time as they notice them.

**Caught during migration work, before any of the above was built — another real gap found by testing against production-shaped data, not by reading `models.py`:** `accounts.simplefin_connection_id`'s foreign key has never actually existed in any real installation's database. The old `_ADDED_COLUMNS` stopgap added the column via a plain `ALTER TABLE ADD COLUMN` — SQLite's `ALTER TABLE` can't add a constraint at all — so every database that predates Alembic is missing it, even though `app/models.py` has declared it from the start. `alembic check` against a copy of the real `data/finance.db` is what surfaced this (a fresh scratch database didn't show it, since a real `CREATE TABLE` includes the constraint from the start — only a database that actually lived through the old stopgap does). **Verified live against the real `data/finance.db`** (same discipline as every phase): backed it up, then applied both new migrations for real — confirmed the exact same result the test suite already proved against a byte-identical copy (1,283 transactions, sum unchanged at $8,227.89, all backfilled `is_transfer = 0`, the FK now present). **Deliberately not done:** no automatic/background transfer-pair scanning — candidates only surface after a human first marks a transaction (matches the SimpleFin new-account discovery-gate philosophy: never silently apply a heuristic match).

## Transactions page redesign ✅ (2026-08-30)

Not part of the six-feature batch's phase sequence — a standalone UI pass, done in response to real usage feedback once Phases A and B had both landed their own per-row controls on the same page. Full design doc: [`docs/2026-08-30-transactions-page-redesign.md`](docs/2026-08-30-transactions-page-redesign.md).

- [x] **Fixed a real performance problem**, not just a perceived one: the list route had no pagination and no eager loading, so `transaction.account`/`.category`/`.tags`/`.transfer_pair` were all lazy-loaded per row — thousands of extra queries at 1,000+ real transactions, which is what "switching between views feels slow" actually was. Fixed with `routers/transactions.py::_base_query()` (`joinedload` for the many-to-one relationships, `selectinload` for `tags`) plus pagination at 100/page (`PAGE_SIZE`). Verified live against the real database (1,375 rows, 14 pages): ≈70ms per page load.
- [x] **Select-then-act replaces one HTMX control per row per action.** A checkbox per row, a fixed bulk action bar (Mark as transfer / Mark as reimbursable / Mark as resolved / Delete) that only appears once something's checked. Category assignment stays its own always-visible per-row control — confirmed with the user first — since it's the page's highest-frequency action and routing it through selection would add friction to the thing done most often here.
- [x] **Selecting 2 and clicking "Mark as transfer" pairs them directly**, replacing the old per-row candidate-suggestion-then-link UI entirely — `transfers.find_transfer_candidates()` is gone (nothing called it anymore once this shipped). Selecting 1 marks/unmarks it alone (toggle, preserving the correction path); 3+ is rejected (no sensible pairing semantic). Reimbursable/resolved follow a single-toggles, multi-only-adds pattern (see the doc for why bulk-remove isn't offered).
- [x] **Delete is new** — hard delete, `hx-confirm`'d, reusing Phase A's `transfers.clear_pair_on_delete()` and explicitly clearing `Transaction.tags` first so no orphaned `transaction_tags` row survives (verified directly against the real database, not assumed from ORM cascade behavior).
- [x] **"All"/"Owed to me"/"Resolved" became one real `<select>`** (`?view=`), replacing three hand-coded links, mapping to the same underlying `(tag, resolved)` filters Phase B already used.
- [x] The whole page gained an HTMX fragment mode (mirroring `dashboard.py`), so filtering/paging/bulk actions never trigger a full reload — directly addresses the reported slowness alongside the query-side fix above.
- [x] `tests/test_transactions.py` rewritten around the new endpoints (26 tests total: bulk actions, `view=` filtering, pagination, category unchanged); 6 now-dead `find_transfer_candidates` tests removed from `tests/test_transfers.py` rather than left alongside the replaced feature.

**Caught during implementation:** httpx's `TestClient` doesn't support a list of `(key, value)` tuples for a repeated form key (`data=[("transaction_id","1"),("transaction_id","2")]` silently sends an empty body) — needs `data={"transaction_id": ["1","2"]}` instead. Real browser/HTMX form submissions were never affected; this only broke the new bulk-action tests until traced down (all ten initially failed with 400s from what looked like a router bug but was a test-harness encoding gap).

**Verified live against the real `data/finance.db`:** timed the new paginated page as above; confirmed `?view=owed`/`?view=resolved` against real data the user had already tagged between sessions (4 open, 1 resolved — more organic Phase B validation, not test data); exercised tag-then-delete and mark-as-transfer against throwaway rows inserted and removed for the purpose, confirming no orphaned `transaction_tags` rows survive a delete and that a transfer mark round-trips cleanly against the real schema — never against real financial rows for anything destructive.

**Deliberately not done:** bulk-remove of a tag/mark (single-selection toggle only); additional filter dimensions beyond the existing three, per the user's call; "select all matching the filter across every page" (current-page-only); soft-delete/undo.

### Round 2 — page size, description truncation, two follow-up bugs (2026-08-30)

Real usage feedback, same day: 50/page reads better than 100; the table still needed horizontal scrolling because of long descriptions — the opposite of the point of this redesign. Full writeup in `docs/2026-08-30-transactions-page-redesign.md`'s "Round 2" section.

- [x] `PAGE_SIZE` → 50. Long descriptions (>60 chars) now collapse behind a native `<details>`/`<summary>` — truncated preview, click to expand in place, no JS.
- [x] **Root cause of the horizontal scrolling, found and fixed**: the original redesign's own `.txn-table td:nth-child(3)` rule (meant to let Description wrap) went stale the moment the redesign's new checkbox column shifted Description from 3rd to 4th — a real regression in the redesign itself, not a missing feature. Replaced with a class-based selector immune to future column reordering.
- [x] A CSS specificity bug in that fix (a single-class selector losing the cascade to a more-specific `.txn-table td` rule, invisible in an HTML diff — only showed up as a status pill rendering on top of the Amount column in an actual screenshot) and a Jinja `truncate()` gotcha (its default `leeway=5` skips truncating anything only a few chars over the limit — missed by an initial test using an over-100-char string that never exercised the gap) — both caught by testing against real ~65-char bank descriptions and a full headless-Chrome screenshot pass, not just text assertions.

### Round 3 — deselect all, toolbar placement, account delete ✅ (2026-08-30)

- [x] **"Deselect all"** button added to the bulk action bar (`static/js/transactions.js`) — clears every checked row checkbox plus the header's "select all" checkbox and resets the bar's count/visibility, same event-delegation approach as the rest of the file.

### Round 4 — toolbar always visible, not pop-in (2026-08-31)

Real usage feedback: round 3's show/hide bulk action bar (hidden until something's checked, `display: none` → `flex`) wasn't what was wanted — the bar popping in and out read as unstable, and the filter and bulk actions read as two disconnected pieces rather than one control strip. **Supersedes round 3's bar-visibility approach** — the "moved to top-sticky" part of round 3 stands, but "toggling visibility" doesn't: it's now toggling `disabled` instead, and the filter + actions are one element, not two.

- [x] **The filter and bulk-action toolbar merged into a single always-rendered `.txn-toolbar`**, inside `transactions/_content.html` (previously the action bar lived outside the HTMX swap target specifically so it wouldn't flicker on every swap — no longer needed, since it doesn't show/hide anymore, so there's nothing to flicker; merging it in also means the filter and toolbar are trivially one sticky unit now, resolving round 3's explicitly-deferred "would need an out-of-band swap" tradeoff for free rather than actually building one).
- [x] Every bulk action button (Deselect all, Mark as transfer, Mark as reimbursable, Mark as resolved, Delete) is always present in the HTML, starting `disabled` — `js/transactions.js` now toggles the `disabled` attribute based on whether any row checkbox is checked, instead of toggling the whole bar's `display`. Same event-delegation/`htmx:afterSwap`-reset structure as before, just a different thing being toggled.
- [x] Verified the actual client-side behavior (not just the static disabled-by-default HTML) with a small standalone test harness loading the real `transactions.js` in headless Chrome and dispatching real `change`/`click` events — confirmed check-one-row enables every button, "select all" counts correctly, and "Deselect all" clears every checkbox (including the header's select-all) and re-disables everything. This project doesn't have a JS test runner set up, so this was a one-off harness for this change, not something added to the permanent suite.
