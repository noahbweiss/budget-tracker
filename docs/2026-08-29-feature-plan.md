# Plan: Six new features — auto-categorization, budgets, transfers, reimbursement, subscriptions, tags

**Status:** approved by the user (2026-08-29); amended (2026-08-29) after a staff-engineer review, then amended again (2026-08-29) to pull goal/fund budgets out of this batch. **Phase 0 (Alembic), Phase A (Transfers), and Phase B (Tags + Reimbursement) are implemented** — see their dated entries in `PLAN.md`. Phases C–E are not yet started. See `CLAUDE.md`/`PLAN.md` at the repo root for architecture/history context this plan builds on.

## Context

All 5 original phases are shipped and in real daily use. The user now wants six interconnected features that go beyond what `PLAN.md`'s roadmap ever scoped: automatic transaction categorization, a real budgeting system (the actual point of `/plan/`, currently an empty nav stub), special handling for credit-card payments so they stop polluting income/spending totals, "owed to me" reimbursement tracking, subscription/recurring-payment detection, and a tagging concept to support several of the above. These were gathered via two rounds of clarifying questions (`AskUserQuestion`) and grounded against the actual current schema/services via an Explore pass and a Plan-agent design pass. A follow-up staff-engineer review then checked every claim in this plan against the live code and flagged real gaps and two over-built pieces — those findings are folded in below, marked where they changed something. UI work continues to be sequenced separately via the user's own Figma wireframes, so this plan scopes backend/data/routing work precisely and UI only at a placement/sketch level.

**Confirmed decisions (do not re-litigate):**
1. Tags, reimbursement, and subscriptions share one general tag system under the hood, but tags are a **small fixed system-defined set** (not user-creatable like categories).
2. Period budgets support **both** per-category budgets **and** an optional overall-total-per-period budget.
3. Period budgets **reset every period** — no rollover.
4. Transfers are marked **manually**; marking one side suggests a match on the other side (reusing `account_merge.py`'s matching pattern) but an unpaired single-side mark is fully valid.
5. Auto-categorization uses **user-defined keyword/substring rules**, auto-applied to new transactions going forward plus a one-time backfill, and **never overwrites** an existing category.
6. Reimbursement resolution is a **simple manual checkbox** for this batch — no linking to the actual incoming payment, no split/partial amounts. (Explicitly flagged for later: subdividing a payment, tracking who owes what per subdivision, and matching an incoming payment to check off subdivisions.)
7. Goal/fund budgets (a named, date-ranged budget like an annual travel fund) are **deferred entirely out of this batch** — see "Deferred: Goal/fund budgets" below. This batch builds one budget type only: the universal period budget (per-category + optional overall total, weekly/monthly/etc., resetting each period). Goals become their own future phase once period budgets are in real use.

**Amendments after staff review (2026-08-29):**
- **Added a Phase 0**: adopt Alembic before any of this batch's schema changes land, instead of adding yet more raw `_ADDED_COLUMNS` entries. This batch is the biggest schema churn the app has seen (5 new tables, several new columns on `transactions`, the first-ever `NOT NULL DEFAULT` case) — the exact inflection point `CLAUDE.md`/`PLAN.md`'s existing Alembic TODO was waiting for.
- **Dropped `post_import_hooks.py`** — it wrapped exactly one call with no second consumer; `import_csv.py` and `simplefin_sync.py` now call `categorization.apply_rules()` directly.
- **Added real integrity work to Phase A**: `transfer_pair_id` behavior on delete/merge, and an explicit statement that transfers still count in `balances.py`.
- **Added a preview step to the categorization backfill** (Phase C), matching the app's existing "review before mutate" convention (SimpleFin new-account gate, merge preview).
- **Stated explicitly** (Phase B) that a reimbursable expense counts fully as spending until resolved, and resolving it never retroactively changes historical dashboard totals — this followed from decision #6 but wasn't written down before.
- **Added a validation rule** (Phase D1): a `PeriodBudget` can't target an income category.
- **Kept the `Tag`/`TransactionTag` join table as designed**, despite the review recommending a plain `is_subscription` boolean instead for this batch's 2-slug vocabulary — see the note in Phase B for why this one recommendation was *not* applied.
- Two factual corrections folded into the phase text below: the import/sync hook needs a small refactor to collect newly-created rows (not a free call), and `ensure_system_tags()`'s per-slug idempotency is justified by tags being code-owned and non-deletable-by-design, not by a later phase adding a slug (both slugs are defined together in Phase B).

**Further amendment (2026-08-29, later same day):** goal/fund budgets (D2 — the travel-budget-style feature) are pulled out of this batch entirely, per the user's explicit call. This batch now ships one budget type: a universal period budget (per-category + optional overall total). Goal/fund budgets, and the other budget "types" the user originally described (travel, a payment budget, rent, etc.), become their own future phase after period budgets are live and in use. The D2 design work already done isn't thrown away — it's preserved under "Deferred: Goal/fund budgets" below so the next phase doesn't start from zero.

## Cross-cutting architecture

- **Transfers are two columns on `Transaction`, not a tag**: `is_transfer: bool` + `transfer_pair_id: int | None` (self-referential FK). A tag table has no natural place to hold a pairing relationship, and transfer-exclusion is a hot-path filter on every dashboard query — a plain indexed boolean beats a join through a tag table.
- **Tags cover exactly two fixed slugs this round**: `"reimbursable"`, `"subscription"`. New `Tag` + `TransactionTag` (many-to-many) tables; `Transaction.reimbursed: bool` stays its own column (only meaningful for the reimbursable tag, so it doesn't belong on the generic join row).
- **Transfers are excluded from `get_period_dashboard()`'s totals/buckets/by_category** (broad — never real income/spending) **but still count in `resolve_balance()`'s "starting_balance + net" tier** (`app/services/balances.py`) — a transfer genuinely moves money into or out of each individual account, so a per-account balance that dropped transfer amounts would stop matching the real bank balance. Only `aggregation.py`'s income/spending/budget math excludes them; `balances.py` is untouched. (Flagged by staff review §4B — the original draft of this plan never stated this and someone implementing "exclude transfers everywhere" could have broken balance accuracy.) *(The plan originally also described a narrower exclusion for goal-assigned transactions from just the budget comparison — that's deferred along with goal budgets themselves; see "Deferred: Goal/fund budgets" below.)*
- **Build Transfers before Budgets**: the new budget-actual query needs the `is_transfer` filter from day one — building Transfers first means `aggregation.py`'s "what counts as spending" logic gets touched once, not twice.
- **Budgets are one table this batch**, `PeriodBudget` — `GoalBudget` (a second table for date-ranged, accumulating fund budgets) is designed but deferred; see "Deferred: Goal/fund budgets."
- **A new `aggregation.get_budget_summary()` function**, not an extension of `get_period_dashboard()` — keeps budget-vs-actual math out of the function everything else on the dashboard depends on. Reuses the existing exported `period_bounds()` helper so budget offset-navigation is free.
- **Auto-categorization runs via a direct call, not a shared hook module.** The original draft proposed a `post_import_hooks.py` dispatch layer; staff review correctly called this a framework built for a single consumer, since subscription detection was already routed *around* it. `import_csv.py::confirm()` and `simplefin_sync.py` instead each collect their newly-created `Transaction` rows and call `categorization.apply_rules(db, new_rows)` directly, right before their existing commit. Revisit the indirection only if a second real post-import behavior shows up later.
- **Subscription detection: review-once discovery gate**, reusing the exact shape of `simplefin_sync.py`'s new-account review step — detected candidates (grouped by account+description+amount, ≥2 occurrences at a roughly regular interval) get a confirm/dismiss step; confirming just applies the `"subscription"` tag, unifying with the tag system rather than inventing a second "confirmed" concept.
- **Category rules match by explicit priority order, first-match-wins** (not an implicit "most specific" heuristic) — transparent and debuggable, matches the mental model of mail-filter rules users already have.

## Build order and phases

**0. Migrations — adopt Alembic** (new, ahead of everything else)

This batch adds 4 new tables (`Tag`, `TransactionTag`, `CategoryRule`, `PeriodBudget`) and 3 new columns on the existing `transactions` table (`is_transfer`, `transfer_pair_id`, `reimbursed`), including the first `NOT NULL DEFAULT` case `_ADDED_COLUMNS` has ever needed. `CLAUDE.md`/`PLAN.md` already flag the `_ADDED_COLUMNS` stopgap as temporary, "reach for actual Alembic once the schema is far enough along to justify it" — this is that point.
- Add `alembic` to `requirements.txt` (exact-pinned version per the project's existing `==` convention — pin whatever's current stable at implementation time).
- `migrations/` at repo root (sibling to `app/`, `tests/`, `docs/`) via `alembic init`; `env.py` configured to import `app.models.Base` and the app's `Settings`-derived DB URL for autogenerate.
- One baseline revision capturing the **current, already-shipped schema exactly** (all 4 existing tables plus every existing `_ADDED_COLUMNS` entry merged in) — this is what `alembic upgrade head` runs for a brand-new empty SQLite file (a fresh clone/`docker compose up`).
- **Existing databases are the tricky part**: the user's real `data/finance.db` (and any forked user's own DB) already has this exact schema live, from `create_all()` + `_ADDED_COLUMNS` having already run historically. It must be `alembic stamp head` (mark "already at this revision," no DDL replayed), never `alembic upgrade head` from scratch (which would try to `CREATE TABLE` on tables that already exist and fail). `app/database.py`'s startup needs a one-time branch: no `alembic_version` table but the app's own tables already exist → stamp; genuinely empty DB → real `upgrade head`. This replaces `Base.metadata.create_all()` + `ensure_schema_migrations()` at startup — delete both only after verifying the stamp path against the real `data/finance.db`.
- Every Phase A–E schema change below becomes a real `alembic revision --autogenerate` script (hand-reviewed before commit, per Alembic's own norms), not a new `_ADDED_COLUMNS` tuple.
- `README.md` gets a one-line note only if `alembic upgrade head` needs a manual step — recommend running it automatically at startup instead, keeping the "clone and run, zero config" principle `create_all()` already established.
- Tests: keep `tests/conftest.py`'s `db_session` fixture using `create_all()` directly against the models for speed (Alembic's job is real-database upgrade safety, not schema definition, so tests don't need to run every migration). Add a new `tests/test_migrations.py`: `alembic upgrade head` from empty against a throwaway on-disk SQLite file, and a stamp-then-upgrade check against a hand-built "legacy" (pre-Alembic, `_ADDED_COLUMNS`-shaped) file — mirroring the existing pre-migration hand-built-SQLite-file pattern already used for `ensure_schema_migrations()` in `tests/test_database.py`.

**A. Transfers** (do first — fixes a real existing bug where an unmarked transfer currently inflates both `totals.income` and `totals.spending`)
- `app/models.py`: `Transaction.is_transfer` (bool, default False), `Transaction.transfer_pair_id` (nullable self-FK).
- Migration (via Alembic now, not `_ADDED_COLUMNS`): add both columns to `transactions`, `is_transfer` as `NOT NULL DEFAULT 0`.
- New `app/services/transfers.py`: `mark_as_transfer`, `find_transfer_candidates` (opposite sign, same magnitude, different account, ±3 days, not already paired), `link_transfer_pair` (sets both sides symmetrically), `unmark_transfer` (clears `is_transfer` and, if paired, unlinks *both* sides symmetrically — not just the one being unmarked).
- **Transfer-pair integrity (added per staff review §4A):** `transfer_pair_id` is a self-referential FK with no story, in the original draft, for what happens when one side disappears. `account_merge.execute_merge()` deletes discarded duplicate transactions and reassigns the rest to the surviving account — neither path currently knows about `transfer_pair_id`. Scope for this phase: (1) when a transaction with a transfer pair is deleted (via merge's discard path or any future delete), null out its partner's `transfer_pair_id` and clear the partner's `is_transfer` if that leaves it unpaired — reuse `unmark_transfer`'s logic rather than duplicating it; (2) when a merge would leave both sides of a transfer pair on the *same* resulting account (the two accounts that had the transfer between them are being merged into one), the pair is no longer a transfer at all — clear both sides' `is_transfer`/`transfer_pair_id` during `execute_merge()`.
- `app/routers/transactions.py`: `POST /transactions/{id}/transfer` (toggle + inline candidates), `POST /transactions/{id}/transfer/link`.
- `app/services/aggregation.py`: add `.filter(Transaction.is_transfer.is_(False))` to `get_period_dashboard()`'s base query (`app/services/aggregation.py:83-85`) — fixes totals/buckets/by_category uniformly for single-account and all-accounts views in one change.
- UI: per-row action on `transactions/_row.html` (frequent, per-row → HTMX, matching the established convention), not a whole-page review gate. Add a small "excludes N transfers this period" caption to the Overview dashboard (matching `balance_caption`'s transparency convention — per staff review §4D, a $500 credit-card payment silently vanishing from the totals with no explanation would be confusing).
- Tests: new `tests/test_transfers.py` (mark/candidates/link/unmark, the unpaired-is-valid case, delete-side cleanup, merge-collapses-a-transfer case); extend `tests/test_transactions.py`, `tests/test_aggregation.py` (transfer excluded from totals but still counted by `balances.py`), `tests/test_account_merge.py`.
- Deferred: no automatic background transfer scanning — candidates only surface after a human first marks a transaction.

**B. Tag system + Reimbursement**
- `app/models.py`: new `Tag`, `TransactionTag` tables, `Transaction.tags` relationship, `Transaction.reimbursed: bool`.
- Migration: new tables (no data migration needed) + `reimbursed` column on `transactions` (`NOT NULL DEFAULT 0`).
- New `app/services/tags.py`: `SYSTEM_TAGS = [("reimbursable","Reimbursable"), ("subscription","Subscription")]`, `ensure_system_tags(db)` — per-slug idempotent, unlike `ensure_default_categories()`'s empty-table-only check. *(Corrected rationale, per staff review §1: both slugs are defined together right here in Phase B, not added incrementally later — the real reason for per-slug idempotency is that, unlike categories, tags are code-owned and not meant to be user-renamed or deleted, so re-checking on every startup safely repairs a lost/missing row with no risk of clobbering user data.)* Wire into `app/main.py` next to the existing `ensure_default_categories(_startup_db)` call.
- **Why the join table stayed** (staff review §2 recommended dropping `Tag`/`TransactionTag` for a plain `Transaction.is_subscription` boolean, arguing a 2-slug vocabulary doesn't justify the machinery): this is the one review recommendation *not* applied. The user was asked exactly this tradeoff directly — "one general tag system under the hood" vs. "separate purpose-built fields" — and explicitly chose the general mechanism, while also confirming tags stay non-user-creatable. That's a deliberate choice about the underlying mechanism, not an oversight; a boolean and a join table both satisfy "not user-creatable," so the review's simplification doesn't actually serve the stated goal, it just picks the other option that was already considered and declined. Keeping it. (If a third system tag or genuine user-facing tagging shows up later, this is also less rework than migrating off two booleans at that point.)
- `app/routers/transactions.py`: `POST /transactions/{id}/tags/{slug}/toggle`, `POST /transactions/{id}/reimbursed/toggle`; `list_transactions()` gains `?tag=`/`?resolved=` query filters.
- **Reimbursable × spending totals (added per staff review §4E):** a reimbursable expense counts fully as spending from the moment it's imported/created — flagging it "reimbursable" doesn't touch `aggregation.py` at all. Resolving it (checking the box) also changes nothing about historical dashboard totals for periods it already appeared in — `reimbursed` is purely a status field for the reimbursement list/tab, not an aggregation input. This was implied by decision #6 ("simple checkbox, no linking") but never written down; stating it here so a future implementer doesn't wire a retroactive total-adjustment that was never asked for.
- UI: tag chips + reimbursed checkbox on `transactions/_row.html`; reimbursement's "separate tab" satisfied as filter-tabs on the existing Transactions page (`All`/`Reimbursable`) rather than a whole new router+templates — **flag this placement for the user's UI pass**, a standalone `/reimbursements/` page is a reasonable alternative if the tab feels buried.
- **Test fixtures (added per staff review §4G):** `tests/conftest.py`'s `db_session` fixture only runs `create_all()` — it doesn't seed system tags (or default categories, or run schema migrations). Phases B–E's tests need system tags to exist. Extend `conftest.py` with a fixture (or extend the existing `client`/`db_session` fixtures) that also calls `ensure_system_tags(db)`, matching how the app itself bootstraps at real startup.
- Tests: new `tests/test_tags.py`; extend `tests/test_transactions.py`.
- Deferred (add to `PLAN.md`'s Later/unscheduled, per explicit user instruction): splitting a reimbursement into subdivisions, per-person tracking, matching an incoming payment to check off subdivisions.

**C. Auto-categorization**
- `app/models.py`: new `CategoryRule` table (`category_id` FK, `pattern` string, `priority` int, `created_at`).
- Migration: new table only.
- New `app/services/categorization.py`: `apply_rules(db, transactions)` (priority order, first match wins, only fills `category_id IS NULL`), `backfill_uncategorized(db)`.
- **Hook wiring (no `post_import_hooks.py` — see cross-cutting section):** `import_csv.py::confirm()` collects the `Transaction` objects it creates in its existing loop and calls `categorization.apply_rules(db, new_txns)` right before its existing `db.commit()`. `simplefin_sync.py::_sync_transactions()` currently returns only counts to its three callers (`sync_matched_accounts()`, `create_new_account()`, `link_to_existing_account()`) — per staff review §1, this needs a small, real refactor (not a free hook call) to also return the newly-created `Transaction` objects so each caller can pass them to `apply_rules()` before its own commit.
- **Backfill preview step (added per staff review §4C):** `backfill_uncategorized(db)` would otherwise silently mutate `category_id` on potentially hundreds of historical rows with no review — inconsistent with the app's established "review before mutate" pattern (the SimpleFin new-account gate, the merge preview). Add a preview: `POST /settings/rules/backfill/preview` runs the matching logic read-only and renders "N transactions will be categorized as follows: …" (grouped by target category), with a separate `POST /settings/rules/backfill/confirm` that actually applies it.
- **Categorization timing on SimpleFin's new-account gate (noted per staff review §4F):** `link_to_existing_account()` pulls recent history into an account that may already have older CSV history. The freshly-synced rows get auto-categorized by the hook; the pre-existing CSV rows don't, until a manual backfill run. This is expected, minor behavior, not a bug — worth surfacing in the rules-management UI copy (e.g. "run backfill after linking a new SimpleFin account") rather than silently leaving a user to notice the inconsistency.
- Fill in real content on `app/routers/settings.py` (currently a stub): `GET/POST /settings/rules`, delete, move-up/down reorder (HTMX), the backfill preview/confirm routes above.
- New templates: `settings/rules.html`, `settings/_rule_row.html`, `settings/_backfill_preview.html`.
- Tests: new `tests/test_categorization.py` (priority order, first-match-wins, never-overwrites, backfill + its preview); extend `tests/test_settings.py`, `tests/test_import_router.py`, `tests/test_simplefin_sync.py` (rule auto-applies on fresh import/sync; already-categorized transactions stay untouched even when a rule would also match).
- Deferred: full category-management CRUD (rules just reference the existing fixed set), drag-and-drop reordering (simple up/down buttons instead), multi-condition rules (amount/account scoping) — description-substring only.

**D. Budgets — period budgets only, this batch's one budget type**
- `app/models.py`: new `PeriodBudget` table (`range_type`, `category_id` nullable = overall-total, `amount`). New `aggregation.get_budget_summary(db, range_type, offset=0, today=None)`, reusing `period_bounds()`. New `app/services/budgets.py` (upsert enforcing "≤1 overall + ≤1 per category per range_type" at the app layer — SQLite treats NULL as distinct in unique constraints, so this can't be a DB constraint). **Category-kind validation (added per staff review §4H):** `category_id` is a free FK today, so nothing stops a `PeriodBudget` pointing at an income category, making the "budget vs. actual" comparison meaningless for that row — the upsert in `budgets.py` rejects `category.kind != "expense"`, and the budget-creation form's category `<select>` only offers expense categories. Fill in `app/routers/plan.py` (existing stub) with the same HTMX-fragment-vs-full-page + offset-navigation pattern as `dashboard.py`. New templates under `plan/`.
- Tests: new `tests/test_budgets.py` (upsert rules including the income-category rejection); extend `tests/test_aggregation.py` (budget math, offset navigation, overall-total budget, transfer exclusion), extend `tests/test_plan.py`, `tests/test_transactions.py`.
- Deferred: rollover (confirmed intentional, not an oversight), income budgets, rich over-budget visual treatment (left to the Figma UI pass), and **goal/fund budgets** — see below.

**Deferred: Goal/fund budgets** (pulled out of this batch by the user — 2026-08-29)

Originally scoped as this batch's "D2." The user wants period budgets shipped and in use first; goal/fund budgets (an annual travel budget, a "payment budget," etc. — a named, date-ranged fund a transaction can be explicitly assigned to instead of counting against its category's period budget) become their own later phase. Preserving the design work already done here so that phase doesn't start from zero:
- `GoalBudget` table: `name`, `start_date`, `end_date`, `target_amount`, `created_at`. `Transaction.goal_budget_id` (nullable FK) on the existing `transactions` table.
- `get_budget_summary()`'s actual-spend query would gain a `Transaction.goal_budget_id.is_(None)` filter alongside the transfer filter — a hard dependency on `PeriodBudget`/`get_budget_summary()` already existing, which is exactly why this phase had to come after period budgets regardless of the timing decision made today.
- The exclusion is narrow, not broad: a goal-assigned transaction was confirmed to stay fully visible in the Transactions list, the category donut, and `get_period_dashboard()`'s totals — it's excluded *only* from the period-budget-vs-actual comparison. Least-surprising-to-the-user reasoning: the expense is real and belongs to its category; a goal fund just means "don't count this against my regular weekly/monthly discipline," not "hide this."
- `budgets.py` would gain goal CRUD + `get_goal_progress(db, goal_budget_id, today=None)` (`{spent, target, remaining, days_left}`, spending-cap semantics — matches the "$1,200 of $3,000 spent" framing, not a savings-accumulation goal type).
- `plan.py` would gain goal routes (`GET /plan/goals`, `POST /plan/goals`, `GET /plan/goals/{id}`); `transactions.py` would gain a goal-assignment route mirroring the category `<select>`.
- The user's other examples (a "payment budget," rent, etc., alongside travel) read as further named instances of this same `GoalBudget` mechanism, not a separate kind of budget — the design above already supports any number of concurrent named goals, so no new mechanism should be needed when this phase is picked up.

**E. Subscription detection** (last — needs Tags from B, most speculative UX of the six)
- New `app/services/subscriptions.py`: `find_candidates(db)` (group by account+description+amount, ≥2 occurrences at a roughly regular interval, ±3 day tolerance, excluding already-fully-tagged groups), `confirm_candidate(db, transaction_ids)` (applies the `"subscription"` tag). Manual tagging (no detection) already works via Phase B's per-row toggle.
- Router: `GET /settings/subscriptions` (confirmed list + monthly-cost rollup + candidates-awaiting-review section) — **flag nav placement for the user's UI pass**: nesting under Settings keeps the nav stable; a dedicated top-level `/subscriptions/` item would be more discoverable but adds nav clutter.
- Tests: new `tests/test_subscriptions.py`; extend `tests/test_settings.py`.
- Deferred: persistent per-candidate dismissal (recomputed fresh each visit — acceptable for a first pass; the review confirms this underbuild is a reasonable, deliberate tradeoff, not an oversight), price-change/cancellation alerts, cross-account subscription merging.

## Verification

- Each phase follows the existing per-router/per-service test-file convention (`tests/test_<name>.py`) and the shared in-memory-SQLite `client`/`db_session` fixtures in `tests/conftest.py`; run `pytest` after each phase, not just at the end.

In particular: verify Phase 0's `alembic stamp head` path against a **copy** of the real `data/finance.db` before ever touching the original, then verify each subsequent phase's real Alembic migration actually upgrades it cleanly.
