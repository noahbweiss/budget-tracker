# Transactions page redesign

**Status:** implemented and verified against real data (2026-08-30); round 2 (page size, description truncation, two follow-up bugs) same day; round 3 (deselect all, account delete — see `PLAN.md`) 2026-08-30; round 4 (toolbar always visible instead of popping in, see `PLAN.md`) 2026-08-31.

## Context

Phases A and B of the six-feature batch (`docs/2026-08-29-feature-plan.md`) each added their own per-row HTMX control to the Transactions page — a "Mark transfer" button plus an inline candidate-linking form, then tag toggle pills and a reimbursed checkbox on top of that. By the time both landed, the page had a real, reported problem: switching between "All"/"Owed to me"/"Resolved" felt slow, the row had gotten cluttered, and there was no way to delete a transaction at all. This is the resulting redesign, done as its own pass rather than folded into a later backend phase, since none of the batch's remaining phases (C–E) touch this page's layout — see the "why now" reasoning in the conversation this was scoped from.

## What changed

**Pagination (100 per page) + eager loading — the actual fix for the reported slowness.** The old list route queried and rendered every matching transaction with no LIMIT — at 1,000+ real rows, and with `account`/`category`/`tags`/`transfer_pair` all lazily loaded per row in the template, that's on the order of 4,000+ queries for a single page load. Pagination alone would have masked this (100 rows × 4 ≈ 400 queries is still slow-ish); the real fix is `app/routers/transactions.py::_base_query()` eager-loading everything up front (`joinedload` for the many-to-one relationships, `selectinload` for the many-to-many `tags`, since a JOIN there would multiply rows). Verified live against the real database (1,375 transactions, 14 pages): a full page load is ~70ms.

**Select-then-act replaces one-HTMX-control-per-action-per-row.** Every row gets a checkbox (`name="transaction_id"`); a toolbar offers *Mark as transfer*, *Mark as reimbursable*, *Mark as resolved*, and *Delete* — all new except transfer/reimbursable, which moved here from their old per-row controls. (Round 1 had this toolbar pop in/out via `display: none` once something was checked; round 4, per real usage feedback, made it always-rendered instead — buttons start `disabled` and get enabled as rows are checked, merged into one persistent strip with the filter dropdown so the two don't read as separate, unstable pieces — see round 4 below.) Category assignment is the one exception, staying an always-visible per-row `<select>`: it's the highest-frequency action on this page, and routing it through select-then-act would add a step to the most common thing done here — the opposite of what this redesign was for. Confirmed with the user before building (multi-select vs. single-select, whether category should move too, whether resolving should join the other bulk actions) rather than guessing.

**Selecting two transactions and clicking "Mark as transfer" pairs them directly**, replacing the old per-row "here's a possible match, click Link" suggestion UI. If you're already selecting both sides yourself, there's nothing left to suggest — `find_transfer_candidates()` and the whole candidate-list UI are retired. Selecting 1 marks it alone (still a fully valid, unpaired end state — see `app/services/transfers.py`); if that one is already marked, it un-marks instead, preserving a correction path. 3+ selected has no sensible pairing semantic and is rejected (400).

**Reimbursable and resolved follow the same single-toggles/multi-only-adds pattern**: select 1 to flip it either way (the correction path), select several to apply the mark to all of them (adding, never removing) — "select 5 dinner charges, flag them all reimbursable" is common; "select 5, strip the tag from all of them" isn't, so bulk-remove isn't offered — remove one at a time instead.

**Delete is new** — hard delete, `hx-confirm`'d client-side. Reuses `transfers.clear_pair_on_delete()` (built for `account_merge.py` in Phase A) so deleting one side of a transfer pair doesn't leave the other pointing at a row that no longer exists, and explicitly clears `Transaction.tags` first so no orphaned `transaction_tags` row survives the delete (verified directly against the real database, not just the ORM's assumed cascade behavior). A deleted transaction can come back on a future CSV re-import or SimpleFin resync if it's still within the sync window, since dedup only skips what's still in the database — not prevented, just worth knowing.

**The "All"/"Owed to me"/"Resolved" links became one real `<select>`** (`?view=all|owed|resolved`), each mapping internally to the same `(tag, resolved)` filter pairs Phase B already used — no change to the underlying query logic, just how a value gets picked. Scope stayed to exactly these three per the user's call, not expanded into a fuller account/category/date filter panel.

**The whole page gained an HTMX fragment mode**, mirroring `dashboard.py`'s established full-page-vs-`_content.html` pattern: filter changes, pagination, and every bulk action's response swap just `#transactions-content`, never a full reload. The bulk action bar's buttons live *outside* that swapped region (so the bar itself doesn't flicker on every action) but read the current `view`/`page` via `hx-include` pointing at hidden inputs that live *inside* it — the same "state that must stay in sync belongs inside the swap target" principle as the dashboard's account sidebar, just applied to two hidden fields instead of a nav list.

## Real gotcha found during implementation

httpx's `TestClient` (used by every router test in this suite) does **not** support a list of `(key, value)` tuples for repeated form keys the way `requests` does — `data=[("transaction_id", "1"), ("transaction_id", "2")]` silently produces an empty body. The correct form is a dict with a list value: `data={"transaction_id": ["1", "2"]}`. This only affects test code — real browser form submissions (and HTMX's own serialization of multiple checked checkboxes sharing a `name`) already produce a normal repeated-key body and were never affected. Caught by the new bulk-action tests initially failing with 400s across the board; worth remembering for any future test that needs to POST a list to this app's endpoints.

## Verified live against the real `data/finance.db`

Timed the new paginated page (≈70ms for 1,375 rows / 14 pages, vs. an unpaginated, non-eager-loaded equivalent that would have run thousands of lazy-load queries). Confirmed the `view=owed`/`view=resolved` filters against real data the user had already tagged between sessions (4 open, 1 resolved — more organic validation of Phase B, not test data). Exercised tag + delete and mark-as-transfer against throwaway rows inserted and removed for the purpose (never against real financial rows), confirming no orphaned `transaction_tags` rows survive a delete and that a transfer mark round-trips cleanly against the real schema.

## Round 2 — page size, description truncation, and two follow-up bugs (2026-08-30)

Real usage feedback, same day: 50/page reads better than 100, and the table still needed horizontal scrolling to read a long description — the opposite of what a "no side-scrolling" redesign was supposed to deliver.

- [x] `PAGE_SIZE` dropped from 100 to 50.
- [x] Long descriptions (>60 chars) now collapse behind a native `<details>`/`<summary>` disclosure — a truncated one-line preview by default, click to expand in place and show the full text below. No JS needed; `<details>` is a real HTML element with built-in open/close behavior. Chosen over a hover tooltip (bad on touch, easy to miss) and a positioned popup (clipping/positioning complexity for no real benefit over just expanding in place).

**Two real bugs found fixing this, neither was a design choice:**

1. **A stale CSS selector, introduced by the original redesign itself.** `.txn-table td:nth-child(3) { white-space: normal }` was written back when Description was the 3rd column — the redesign's own new checkbox column shifted it to 4th without updating the selector, so Description silently inherited `nowrap` again and forced the whole table wide enough to fit even the longest bank-generated description on one line. This — not the truncation feature being missing — was the direct cause of the reported horizontal scrolling. Fixed by targeting the column with a real class (`.description-cell`) instead of a fragile position-based selector, which won't break the next time a column is added or reordered.
2. **A CSS specificity bug in the fix for bug 1.** `.description-cell { white-space: normal }` (one class, specificity 0-0-1-0) is *less* specific than `.txn-table td { white-space: nowrap }` (element + class, 0-0-1-1) — the more specific rule wins regardless of which one appears later in the file, so the fix silently lost the cascade and did nothing. Visible as a real rendering bug: a status pill immediately after an unwrapped description line rendered on top of the Category/Amount columns instead of wrapping. Fixed by matching the prefix (`.txn-table td.description-cell`), and applied the same pattern to the Account column pre-emptively. Also switched the table to `table-layout: fixed` with an explicit `<colgroup>` — `auto` layout lets a `max-width` on a cell be overridden by content that "doesn't need" to wrap, which was part of what let this go unnoticed.
3. **Jinja's `truncate()` filter has a default `leeway` of 5** — it leaves a string alone if it's only a few characters past the limit, rather than truncating it "for just a little." A real bank description ~65 characters long (5 over the 60-char threshold here) was rendering in full, untruncated, until pinned with an explicit `leeway=0`. Caught by testing against a real 65-char description from the live database, not a synthetic one — a hand-picked test string safely over 100 chars (used for the first truncation test written) wouldn't have hit this gap at all.

**Verified live against the real `data/finance.db`**, including a full headless-Chrome screenshot pass (not just `curl`/text assertions) — this class of bug (visual overlap, a rule silently losing the cascade) doesn't show up in an HTML diff, only in a rendered page.

## Round 4 — the toolbar shouldn't pop in (2026-08-31)

Real usage feedback: round 1's bulk action bar (hidden via `display: none` until a row got checked) read as unstable — buttons appearing/disappearing rather than being reliably *there*. The fix requested was specific: the toolbar should always be visible, action buttons present but disabled/greyed-out until something's selected, and it should read as one connected filter-and-actions strip rather than two separate pieces.

- [x] Merged the filter dropdown and the bulk action buttons into one `.txn-toolbar` element, always fully rendered inside `transactions/_content.html` (previously the action bar deliberately lived *outside* the HTMX swap target specifically to avoid flicker from its own show/hide toggling — once nothing about it shows/hides anymore, that reason for keeping it separate goes away, and merging it in is what made "one sticky unit with the filter" trivial instead of needing the out-of-band-swap machinery round 3 explicitly declined to build).
- [x] Every action button (Deselect all, Mark as transfer, Mark as reimbursable, Mark as resolved, Delete) starts `disabled` in the rendered HTML; `js/transactions.js` toggles the `disabled` attribute on checkbox change instead of toggling the bar's `display`.
- [x] Verified the actual interactive behavior — not just that buttons render `disabled` by default — with a small standalone HTML harness that loads the real `transactions.js` and dispatches genuine `change`/`click` events in headless Chrome: checking one row enables every button and updates the count, "select all" counts correctly, and "Deselect all" clears every checkbox (including the header's select-all) and disables everything again. This project has no JS test runner, so this was a one-off verification harness for this specific change, not something folded into the permanent suite.

## Deliberately not done

- Bulk-remove of a tag/mark across multiple selected transactions — only single-selection toggles support removal; see the reimbursable/resolved reasoning above.
- Additional filter dimensions (account, category, date range) — scope stayed to restructuring the existing three, per the user's call.
- "Select all matching the filter across every page" — select-all only ever applies to the current page's 100 rows.
- Soft-delete/undo/trash — a plain hard delete, matching the level of a first pass; revisit if accidental deletion turns out to be a real problem in practice.
